## 1. Product Identity

Maya is the experimental v2 Agent7even product: an AI-first marketing workspace for small businesses.

Maya is not just a chatbot. Maya is the intelligence layer across:

- campaigns
- agents
- services
- content calendar
- brand kit
- analytics
- deliverables
- support
- billing/team/account operations

The canvas is the workspace. Maya is the command line and strategist that understands the workspace.

Core product rule:

> Maya should help with the user's current work, not behave like a generic chat shell.

## 3. Maya Context Behavior

Maya should know what page/module the user is working on.

Implemented behavior:

- Pages dispatch `maya:canvas-context`.
- Chat requests include `canvasContext`.
- Maya sessions store `canvas_context`.
- Maya chat history can be deleted from the sidebar.
- Delete controls should remain quiet and hover-based where practical.

Expected behavior:

- On Services, Maya understands active orders, selected order, and available services.
- On Agents, Maya understands selected agent, output counts, approvals, and current setup form.
- On Deliverables, Maya understands available files/projects.
- On Calendar, Maya understands current schedule and content gaps.
- On Brand Kit/Foundation, Maya understands brand context and should write in that voice.

Maya should not force the user to repeat visible page context.

## 4. Agents

There are nine agents. They should not share one generic setup flow.

Agent flows must collect the context needed for each specific agent to produce a finished output.

Current agent product rules:

- Auto agents save outputs directly to `agent_outputs`.
- Approval agents route to the approval queue.
- Auto-agent outputs must still be visible from the Command Center.
- Scorecard output counts are not enough; users need to open and read the actual content.
- Agent output detail pages should be structured by output type where possible, not raw markdown dumps.

Agent output surfaces:

- `/dashboard/agents` — Command Center
- `/dashboard/agents/[agentId]/outputs` — archive/detail level below Command Center
- `/dashboard/agents/approvals` — approval queue

Important UX rule:

> An output that asks the user for missing inputs is a failed run unless the flow explicitly intended a clarification step.

## 5. Services

Services is no longer just a request modal. It is a trackable service/order workspace.

Services page responsibilities:

- Browse available services.
- Request managed services.
- Generate free self-serve assets.
- Track active and completed orders.
- Keep service follow-up inside Services, not Support.

Managed service behavior:

- Creates an `orders` row.
- Creates linked conversation/support transcript.
- Admin sees the order in Admin Orders.
- Admin can update status and follow up.
- User sees order status and can continue the service conversation in Services.
- In-review/admin-managed orders should not be user-deletable while in review.

Self-serve service behavior:

- Can generate output immediately.
- Does not require admin follow-up.
- Can be repeated as often as needed.
- Can be deleted from Services history if it is a self-serve `viral_hooks` order.
- Permanent assets generated by self-serve flows live in Deliverables.

## 6. Viral Hooks

Viral Hooks is the first free self-serve service.

Service type:

```txt
viral_hooks
```

User flow:

1. User opens Marketing Services.
2. User chooses Viral Hooks.
3. Dedicated generator modal collects:
   - topic/offer
   - audience
   - primary goal
   - best format
   - tone
   - notes
4. Maya generates the hooks immediately.
5. Output is stored in the order brief using `VIRAL_HOOKS_OUTPUT_MARKER`.
6. PDF is saved to Deliverables.
7. User can download PDF from output view and Deliverables.
8. User can mark complete.
9. User can delete the Viral Hooks card from Services history without deleting the Deliverables PDF.

Viral Hooks output framework currently includes:

- Cost-Narration Hooks
- False-Statement Hooks
- Comparison Hooks
- Callout Hooks
- Bold Statement Hooks

Important rule:

> Viral Hooks is not a normal service request. It should feel like a generator/tool, not an admin order.

## 7. Deliverables

Deliverables is the permanent asset/file library.

Live schema is project-backed:

```txt
projects:
  id
  user_id
  title
  description
  phase
  progress_percent
  dates

deliverables:
  id
  project_id
  milestone_id
  title
  description
  file_url
  file_type
  file_size
  version
  uploaded_by
  created_at
```

Do not use the old deliverables schema:

```txt
user_id
project_name
file_name
file_path
notes
uploaded_by_role
```

Current implementation normalizes live rows into a UI shape, but database reads/writes should use:

- `projects.user_id` for ownership
- `deliverables.project_id`
- `deliverables.title`
- `deliverables.description`
- `deliverables.file_url`

Viral Hooks creates/reuses a `Viral Hooks` project.

Allowed project phases confirmed from live Supabase:

- `discovery`
- `strategy`
- `design`
- `development`
- `launch`
- `completed`

Deliverables should support:

- client uploads
- admin uploads
- signed downloads
- user delete where authorized
- project grouping

## 10. Design System and Color Direction

A design-system/color-token pass is planned but not started.

Branch to use:

```bash
design-system/color-tokens
```

Agreed palette:

| Role | Hex |
|---|---|
| Primary / interactive | `#3B82F6` |
| Secondary / dark UI | `#2D3748` |
| Logo accent | `#F5349B` |
| Success / positive | `#10B981` |
| Warning / medium progress | `#FCA509` |
| Danger / low/error | `#EE533B` |
| Neutral surface | `#F8FAFC` |
| Menu muted text | `#9BA1AE` |
| App background | `#FCFCFC` |
| Card/surface | `#FFFFFF` |

Design direction:

- Stripe-like restraint.
- Clean light surfaces.
- Blue for actions, focus, links.
- Dark slate for strong UI.
- Pink only for logo/accent moments.
- Semantic status colors stay semantic.
- Do not globally replace colors blindly by hex; replace by UI role.
